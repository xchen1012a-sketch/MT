# MT5 多终端中控台——技术架构与实施计划书

**版本：** V0.1（技术选型草案）  
**日期：** 2026-11-23  
**建设方式：** 全新开发；现有 SRS 仅作为业务需求参考，不复用旧系统代码或架构。

## 一、项目目标与范围

开发一套可通过电脑和手机浏览器访问的 MT5 多账户监控系统，统一监控多台 Windows 电脑上同时运行的多个 MT5 终端。系统以**只读监控**为边界，不提供下单、平仓或修改订单能力。

主要能力包括：终端发现与账户配对、实时净值/余额/盈亏/持仓、历史曲线、交易与资金流水、当日净值基准、账户与设备状态、风险告警、通知、报表、备份和运维诊断。

核心原则：**成熟开源底座负责通用能力；MT5 采集、金融数据口径和风险业务由项目自行开发。**

## 二、技术选型（拟定）

| 子系统 | 选用技术与开源来源 | 复用内容与职责 |
| --- | --- | --- |
| Web 前端 | React + TypeScript + [Ant Design Pro](https://github.com/ant-design/ant-design-pro) | 复用布局、路由、表格、表单、管理后台组件；自研 MT5 业务页面 |
| 可视化 | [Apache ECharts](https://github.com/apache/echarts) | 净值曲线、每日盈亏柱图、回撤和账户对比 |
| API 后端 | Python + FastAPI；以 [Full Stack FastAPI Template](https://github.com/fastapi/full-stack-fastapi-template) 的 `backend/` 为基础 | 复用后端组织、认证基础、数据访问、迁移与测试配置；自研业务 API |
| 数据库 | PostgreSQL + SQLModel/SQLAlchemy + Alembic | 账户信息、状态快照、持仓、成交、账务、告警及审计 |
| Windows 采集器 | Python + [MetaTrader5 官方 Python 接口](https://www.mql5.com/en/docs/python_metatrader5) | 自研终端识别、进程隔离、只读采样、离线队列、重试和升级 |
| 传输 | HTTPS + JSON；设备身份认证与请求签名 | 设备上报、去重、重传和状态追踪 |
| 部署 | Docker Compose + HTTPS 反向代理 | 云端前后端及数据库一体化部署；Windows 采集器独立安装 |
| 后台任务 | 起步采用独立后台任务进程；负载需要时增加 Redis/Celery | 定时聚合、告警判断、通知发送、补算和清理 |

**整合方式：** 只采用 Ant Design Pro 作为前端底座；舍弃 Full Stack FastAPI Template 自带的 React 前端，提取和适配其后端，重新对接 API、登录状态与权限。固定经过验收的版本，不直接追踪主分支更新。

## 三、项目组织与部署架构

建议采用**一个 Git 主仓库（Monorepo），三个可独立构建和部署的子项目**：

```text
mt5-control-center/
├── frontend/      # Ant Design Pro / React / ECharts
├── backend/       # FastAPI / SQLModel / PostgreSQL
├── collector/     # Windows MT5 采集器
├── deploy/        # Docker Compose / HTTPS / 环境配置
├── docs/          # 架构、需求、API、运维和验收文档
└── tests/         # 跨模块集成与端到端测试
```

业务链路：**Windows 多开 MT5 → 本地 Collector → HTTPS → 云端 Backend → PostgreSQL → 前端 Web**。浏览器通过 API 拉取最新状态；初期用定时增量刷新，确有需要再增加 WebSocket。

采集器在每台 Windows 电脑上统一管理已经登记的 MT5 终端。云端只接收经授权的设备与账户数据，不承担远程操纵交易终端的职责。

## 四、核心实施设计

### 1. 采集与账户身份

- 优先验证官方 Python SDK 指定 MT5 终端路径连接的能力。采用**每个 MT5 终端独立采集进程、统一管理器协调**的候选架构；在真实 GTC 多开环境验证之前不视为已定型。
- 每个账户以“券商服务器 + 登录号”作为业务标识，并校验终端路径、设备、币种及账户切换事件。重复来源须人工确认，不能重复纳入组合汇总。
- 采集端采用只读接口获取余额、净值、保证金、持仓与历史成交；默认不实现交易执行接口。
- 本地记录采样时间与上传状态；断网后保存**已成功采到**的数据，恢复后补传。禁止将补传旧读数标为实时数据。
- 如 Python SDK 无法稳定隔离真实多开终端，再评估自研 MQL5 EA + 本地代理作为备选采集路径。

### 2. 接收、存储与状态

- 采样使用唯一批次标识、设备身份和时间戳；接收端验证授权、签名、时效并进行幂等去重。
- 区分设备心跳、终端连接状态、账户最新采样时间；“没有数据”和“数值为 0”必须区分。
- 最新快照用于看板，历史采样与成交用于图表和对账；迟到数据不能覆盖更新的账户状态。
- 资金金额保留原币并使用定点/Decimal 计算；不同币种不直接相加，换算结果明确标注参考汇率及覆盖范围。

### 3. 财务口径与告警

- 主看板按照北京时间自然日计算日初净值与当前净值之差；若日初样本缺失，标注“待确认”，不以任意日间读数替代。
- **当日净值变化**与**交易盈亏**分开统计；出入金、券商调整与人工记账分别留痕，防止重复计算。
- 风险规则覆盖保证金、浮亏、回撤、采集中断等；后台持续计算，网页关闭不影响告警判断和通知。

## 五、实施阶段与验收门槛

| 阶段 | 核心工作 | 阶段交付及验收 |
| --- | --- | --- |
| P0：技术底座 | 创建 Monorepo；引入两个官方开源底座；建立 API 对接、数据库、登录与 CI | 前后端独立启动；登录和数据库迁移通过；第三方许可证及依赖扫描通过 |
| P1：多开采集验证 | 真实 GTC 终端发现、独立进程连接、账户识别、状态读取、重连 | 用实际多开账户连续测试，确认无串号、无重复汇总、关闭与切换状态正确；形成 SDK/EA 路线结论 |
| P2：最小可用中控（MVP） | 设备配对、安全上传、离线缓存、账户清单、总览、持仓和健康状态 | 从 Windows 采集到网页展示形成闭环；断网补传、旧数据提示和授权撤销通过 |
| P3：完整业务 | 日初净值、历史曲线、成交/资金流水、人工记账、收益与回撤、告警通知 | 统一财务口径；多币种及缺样场景正确；告警可确认、恢复并追溯 |
| P4：交付与运维 | Windows 安装/升级、云端部署、监控、备份恢复、安全加固 | 新设备可独立安装；升级可回退；备份可试恢复；电脑和手机可访问 |

**优先级原则：** 先完成 P1 采集可行性验证，再开展大量业务页面开发。具体采样频率、可承载账户数、延迟和连续运行指标以真实设备测试结果确定，而非提前承诺。

## 六、开源与安全要求

1. 仅从项目官方仓库获取源代码，保留 MIT/Apache 等适用许可证与版权声明；审计依赖和安装脚本，不执行不明二进制文件。
2. 固定依赖版本及锁文件，启用依赖漏洞扫描、代码审查、自动化测试、构建产物校验；正式 Windows 安装包自行构建、签名（具备签名条件时）。
3. 采集器使用最小权限；MT5 凭据尽可能留在运行终端的 Windows 安全存储中，不上传交易密码。
4. 面板用户认证与采集设备认证分离；所有公网通信启用 HTTPS，设备支持暂停、撤销授权和密钥轮换。
5. 云端审计敏感配置修改、设备配对、手工财务调整和告警确认；日志与诊断导出进行脱敏。

## 七、关键风险与待验证事项

- **多开隔离：** 官方 SDK 支持指定终端路径，但多实例并行稳定性、不同安装/数据目录和账号切换行为必须现场实测。
- **会话依赖：** Windows 休眠、注销、MT5 被关闭时无法保证继续采样；系统要准确显示缺口，而不是伪造连续读数。
- **模板整合：** Ant Design Pro 与 FastAPI 模板的登录、API 类型和构建流程需要适配，不能直接把两个仓库合并。
- **业务一致性：** 日初缺失、出入金、交易补传、跨币种换算会直接影响报表，需准备可复现的验收数据集。

## 八、阶段性结论

新中控确定采用 **Ant Design Pro（前端） + Full Stack FastAPI Template 的后端基础 + PostgreSQL（数据库） + 自研 Windows MT5 采集器**。

新旧系统彻底隔离；不复用旧代码。建设从“开源底座审核与整合 → 多开采集验证 → MVP 闭环 → 完整 SRS 功能 → 安全交付”推进。**最终采集实现、性能目标和版本号在 P1 实测后正式冻结。**
